HIGHUnguarded window.open() at game-end navigates to an external URL — tab-napping risk

index.html · Lines 930–932 — endGame()

When the 30-second timer expires, endGame() calls window.open(url, "_blank"). Because no rel="noopener noreferrer" equivalent is passed, the opened tab receives a reference back to the opener window via window.opener. If the destination URL is ever compromised or redirected to a malicious page, the external page can call window.opener.location = "phishing-page.com" to silently redirect the original game tab. This is especially concerning in a live event kiosk context where the tab is unmonitored.

// line 930–932
if (navigator.onLine) {
    window.open("https://eventsn.cxoforum.com/...", "_blank");
    // ← no noopener passed; opener reference is exposed
}
Fix: Pass the noopener and noreferrer features: window.open(url, "_blank", "noopener,noreferrer"). This severs the window.opener reference in the new tab.
HIGHOutdated Three.js r128 — multiple known CVEs and 3 years behind current

three.min.js · Copyright header identifies r128 (2021)

The bundled Three.js is r128, released in 2021. The current stable release is r168+ (2024). Three years of security patches, WebGL context-loss handling improvements, and memory-leak fixes are absent. While no specific RCE CVE is known for Three.js itself, the outdated version means the app misses mitigations for shader injection edge cases and may expose deprecated/removed API behaviour. For a kiosk game running on shared hardware at a public event, keeping dependencies current reduces attack surface.

Fix: Replace three.min.js with the current release (r168+). Download from threejs.org or via npm (npm pack three and extract the minified build). Test existing geometry and material APIs — most are backward-compatible.
HIGHGame timer can be manipulated — setInterval countdown runs in JS, not on a monotonic clock

index.html · Lines 891–901 — startGame() timer

The 30-second countdown uses setInterval(..., 1000) which is not reliable — browsers throttle intervals in background tabs, and the interval can drift significantly under CPU load from the Three.js render loop. At a public event kiosk with many simultaneous Three.js operations, players may get 35–40 seconds instead of 30. Additionally, a user who opens DevTools can call clearInterval(gameTimerInterval) to freeze the timer, then endGame() directly to claim a high score without playing.

// lines 891–901
gameTimerInterval = setInterval(() => {
    timeRemaining--;           // decrements once per interval tick
    // ...
    if (timeRemaining <= 0) endGame();
}, 1000);
// No monotonic start-time check — timer drifts under load
Fix: Record a wall-clock start time: const startTime = Date.now();. In the animate() loop, compute remaining time as Math.max(0, 30000 - (Date.now() - startTime)). This is immune to interval drift and DevTools manipulation of the interval variable.

MEDIUMGamepad Start and Quit buttons share the same physical button (index 9) — pressing Start also immediately quits

index.html · Lines 627–628 — pollGamepad()

buttonStart is mapped to gp.buttons[9] (the standard Start/Options button on most gamepads). buttonQuit is mapped to gp.buttons[8] || gp.buttons[9]. This means pressing Start to begin the game simultaneously sets gpInput.quit = true in the same frame. In animate(), gpInput.quit is checked before the game state fully transitions, which causes the game to start and immediately call quitGame() in some timing windows.

// lines 627–628
const buttonStart = gp.buttons[9] && gp.buttons[9].pressed;
const buttonQuit  = (gp.buttons[8] && gp.buttons[8].pressed)
                 || (gp.buttons[9] && gp.buttons[9].pressed);  // ← same button!
Fix: Remove gp.buttons[9] from the quit mapping. Use only gp.buttons[8] (Select/Back) for quit, keeping Start (9) exclusively for starting the game: const buttonQuit = gp.buttons[8] && gp.buttons[8].pressed;
MEDIUMThree.js geometry and materials are never disposed — progressive VRAM leak on replay

index.html · Lines 561–598 — spawnOpponents(), spawnObstacle(), spawnCollectible()

Every time an obstacle or collectible is removed via scene.remove(obs.mesh), the underlying BufferGeometry and Material objects are not disposed. Each collected key or hit obstacle leaks GPU memory. Opponents are also fully rebuilt on each spawnOpponents() call (which is only called once at startup — but if the game is restarted without a page reload, old meshes accumulate). On a kiosk running for hours with hundreds of game rounds, this will cause the browser to crash or stutter due to VRAM exhaustion.

// line 758–759 (obstacle removal — no dispose)
scene.remove(obs.mesh);
obstacles.splice(i, 1);
// obs.mesh.geometry.dispose() and obs.mesh.material.dispose() are missing
Fix: Before every scene.remove(mesh), call mesh.traverse(child => { if (child.isMesh) { child.geometry.dispose(); if (Array.isArray(child.material)) child.material.forEach(m => m.dispose()); else child.material.dispose(); } });. Also dispose billboard CanvasTexture objects.
MEDIUMScore can go negative — Math.max(0, score - N) not applied consistently

index.html · Lines 732–733 and 753–754

Both collision handlers (opponent and obstacle) correctly clamp the score with Math.max(0, score - N) in the lines shown. However, the displayed score in the HUD (document.getElementById('hud-score').innerText = score on line 794) reads the raw score variable directly. If a collision fires in the same frame as a previous clamping, the displayed value is correct. But there is a secondary issue: on the next frame the clamped value is now stored in score so the display will be correct — but this double-check can display "−0" briefly in edge cases. More importantly, the clamping is applied only in those two paths; a future addition of a time penalty would need to remember to also clamp.

Fix: Centralise score mutation through a helper: function addScore(delta) { score = Math.max(0, score + delta); }. Replace all direct score += and score -= sites with this function.
MEDIUMMissing font files cause layout degradation silently — no fallback notification

css/fonts.css · Lines 3–10 · fonts/PUT_FONTS_HERE.txt

The game requires Orbitron.woff2, Rajdhani-Medium.woff2, Rajdhani-SemiBold.woff2, and Rajdhani-Bold.woff2 in the fonts/ directory. These files are absent from the distributed package. Without them, the browser silently falls back to system fonts. On Windows machines at the event (likely the kiosk platform), the fallback chain (Bahnschrift → Eurostile → Segoe UI) produces noticeably different letter-spacing and sizing for all Orbitron-sized headings, potentially overflowing the fixed-pixel HUD boxes (especially the "VIBE BREAKER" title area and score counters).

Fix: Bundle the four .woff2 files with the project before the event. All four fonts are free under OFL and available from fonts.google.com. Run a visual check at 1080p and 4K on the actual kiosk hardware.

Low

LOWrequestAnimationFrame loop runs at full speed even on the start screen — unnecessary GPU load

index.html · Lines 641–654 — animate()

The animate() function calls requestAnimationFrame(animate) unconditionally at the top, then renders the full Three.js scene even when the game is not active (!gameActive). On the start screen at 60/120 fps, the GPU renders the full snowy city at full resolution continuously — consuming significant power and generating heat on a kiosk machine that may need to run for 8+ hours. The idle scene has no motion other than the render, so a reduced idle frame rate would be imperceptible.

Fix: On the start screen, render at a throttled rate: replace requestAnimationFrame(animate) with setTimeout(() => requestAnimationFrame(animate), !gameActive ? 100 : 0) for a ~10 fps idle rate.
LOWAudioContext is never closed — leaked audio node when page is reloaded or hidden

index.html · Lines 225–248 — initAudio()

The AudioContext (audioCtx) and its connected oscillator are created in initAudio() but never closed on quitGame() or endGame(). The engine oscillator continues running (at zero gain) between games. Each browser tab is limited to a small number of AudioContext instances; on browsers with strict limits (Safari iOS) this will prevent audio from working in later sessions. The oscillator also cannot be garbage-collected while still connected to a running context.

Fix: In both quitGame() and endGame(), stop the oscillator and suspend the context: engineOsc.stop(); audioCtx.suspend();. On the next game start, resume it: audioCtx.resume();. No need to fully close and recreate the context.
LOWTouch controls do not handle mouseleave — button stays "held" if cursor leaves the element

index.html · Lines 843–855 — bindBtn()

bindBtn() listens for mousedown (set true) and mouseup (set false). If the user clicks and drags the mouse off a button, the mouseup fires on the document rather than the button, so the setter is never called with false. The accelerate, brake, left, right, or nitro state remains locked on indefinitely until the button is clicked again. This is particularly noticeable with the ACCEL button in desktop/kiosk mouse mode.

Fix: Add a mouseleave listener that resets the state: el.addEventListener('mouseleave', () => { setter(false); });
LOWObstacle collision uses stored obs.x (spawn position) rather than live mesh position — stale collision

index.html · Lines 751–752 — obstacle collision check

The collision check for obstacles uses obs.x (the value set at spawn time) rather than obs.mesh.position.x. Since obstacles do not move laterally, these are equivalent today. However, if a future update adds obstacle drift or knockback, the collision will silently stop working. The opponent collision already correctly uses opp.mesh.position.x (line 731), creating an inconsistency.

// line 752 — uses stale spawn x
if (Math.abs(obs.x - playerX) < 1.2) { ... }
// should be:
if (Math.abs(obs.mesh.position.x - playerX) < 1.2) { ... }
Fix: Replace obs.x with obs.mesh.position.x in the collision check for consistency and future-proofing.
LOWNo viewport meta prevents pinch-zoom on mobile/tablet touch screens

index.html · Line 5

The viewport meta tag is present but uses only width=device-width, initial-scale=1.0. It does not set user-scalable=no or maximum-scale=1. At a public event kiosk on a touchscreen, participants can accidentally pinch-zoom the entire game interface, breaking the HUD layout and making it unrecoverable without a page reload.

Fix: Add user-scalable=no, maximum-scale=1.0 to the viewport meta: <meta name="viewport" content="width=device-width, initial-scale=1.0, user-scalable=no, maximum-scale=1.0">

Informational

INFONo <meta name="referrer"> — full URL sent to event website on redirect

index.html · Line 931

When window.open() fires at game end, the browser sends a Referer header containing the local file path (file:///Users/.../index.html or the kiosk's serving origin) to the destination server. This leaks the local file system path in server logs. For a local file served from a USB drive, this may expose internal directory structure.

Note: Pass "noopener,noreferrer" as the third argument to window.open() (already recommended under the High finding above) — noreferrer also suppresses the Referer header.
INFOSnow particle system mutates Float32Array every frame — moderate GC pressure

index.html · Lines 707–714 — snow animation in animate()

Every frame, all 6 000 snow particle Y-positions (2 layers × 3 000) are iterated and mutated in place via direct array access, then needsUpdate = true re-uploads the buffer to the GPU. This is the correct pattern for dynamic particles. No allocation occurs per frame, so garbage collection is not a concern here. The comment is for awareness: at 120 fps on a high-refresh kiosk display, this is 720 000 float writes per second — acceptable but worth noting if performance degrades.

Note: No change needed. If frame rate drops become noticeable, reduce snowCount from 3 000 to 1 500 per layer, or move snow to a vertex shader.
INFOThree.js r128 is vendored with no integrity verification or version pinning

three.min.js · index.html line 7

The library is loaded as a local file with no Subresource Integrity (integrity attribute) on the <script> tag. For a file served locally this is acceptable (SRI is for CDN-loaded resources), but it means there is no automated detection if the file is replaced or corrupted on the distribution USB drive. The SHA-256 of the current file is recorded in this report for reference.

Note: Record the SHA-256 hash (9274bbce…) in a CHECKSUM.txt alongside the files, and verify it on each deployment: shasum -a 256 three.min.js.

Positive Findings

✓ No user data collected or stored — the game has no forms, no localStorage writes, no cookies, and no network requests (except the final window.open). Attack surface is minimal.

✓ No innerHTML with user-controlled data — all DOM updates use .innerText, preventing XSS via display values.

✓ Offline-first architecture — the game runs fully offline except for the end-of-game URL open, which is correctly guarded by navigator.onLine.

✓ No eval() calls — the "eval" occurrences in three.min.js are all .evaluate() animation interpolant methods, not code execution.

✓ Touch event preventDefault() applied — touch buttons correctly call e.preventDefault() to block scroll interference during gameplay.
